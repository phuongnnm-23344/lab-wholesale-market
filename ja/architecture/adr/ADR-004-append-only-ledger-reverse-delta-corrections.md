# ADR-004 — 追記のみの台帳、REVERSE / DELTA で修正：当日訂正 / 取消と修正申請を一つの仕組みで

| 状態 | 日付 | 決定者 | 置換 |
|---|---|---|---|
| **Accepted**（§6 の顧客待ちの点を除く） | 2026-11-26 | 受講者（L4-D09）、PL が提案 | — |

## 1. 背景

- ルール4：履歴を上書きしない。確定済みの取引の修正 = 理由付きの依頼 + 決裁 + REVERSE / DELTA の記録。原本は残す（FR-CORR-01/02）。締め済みの日は直接修正しない（BR-CLOSE-01, FR-CORR-03）。
- 日を締める前は、取引を窓口で素早く訂正 / 取消できる必要があり、理由を残し、履歴を保持する。**二段階の決裁は不要**（FR-AITAI-03, PRM-127, M17）。プロトタイプにはまだない — 現状はすべての修正が修正申請を通る（D11）。
- プロトタイプは本線で正しく動いている：確定済みの取引（CONFIRMED）はトリガーで凍結；`trade_adjustments` に REVERSE（旧買受人）+ DELTA（新買受人）；ロット数量の台帳 `lot_quantity_ledger`；追記のみのテーブル 10 個（as-built §2.3）。
- 本番に向けたプロトタイプの欠陥：監査は `app.seeding` で無効化でき、監査を消すリセット関数がある（D19, M24）；取引の状態は2値のみで、FIG-012 に従っていない（D10）。
- 取引は1日 1,200 件、7年 → 件数は小さい（約2,5百万行）。複雑なモデルを選ぶ理由にはならない。

## 2. 決定

1. **確定後の元のレコードは不変。** 取引、せりの結果、引渡し、ロットの数量台帳、入金、奨励金の結果、監査ログ：INSERT のみ；トリガーで UPDATE / DELETE を拒否；アプリの DB ロールはテーブルへの書き込み権限を持たない（ADR-001）。
2. **確定後のすべての変更 = REVERSE + DELTA のペア**。`adjustment_source` を付与：
   - `SAME_DAY` — SC-04-05 での当日訂正 / 取消。取引の業務日が**まだ締められていない**場合のみ；TRADE の役割を持つ者；理由を入力；決裁は不要。**金額が変わる引渡しの例外**（不足 / 返品 / 一部取消 — SC-06-04, SC-06-05）は、日付がまだ開いている場合に限り、役割 **DELIVERY**（紛争の結論を出す場合は DEL-HEAD）が `trade_fixes` を `SAME_DAY` で作成できる。これは**引渡しの例外の関数経由のみ**、`reason_code = DELIVERY_EXCEPTION`、`delivery_exceptions.fix_id` で紐づける（TRADE_DB 0.2.1）。配送は**実際に引き渡した数量のみ入力**（減少方向のみ：不足 / 返品 / 一部取消 — 過剰は記録のみ）、**価格や金額は入力・修正しない** — 金額は確定済みの取引単価から関数が計算する。自分で確認はしない — 照合事務局が日次締めの前に「確認済」を押す（ADR-005 §2.5 項目6）。【顧客（模擬）、2026-11-25 — Q-DEL-04】。取消 = REVERSE のみで DELTA なし；数量はロットの台帳を通じてロットに戻る（BR-LOT-02）。
   - `CORRECTION` — 修正申請。日付が締め済みのとき（または決裁の経路を選んだとき）：理由 + 証拠、1次決裁（照合部門長）、**買受人ごとに変動した金額の最大値**（|Σ 税込の差| の、買受人ごとの最大値）が**規則（ADR-006 のバージョン管理）に定めた閾値以上**なら2次決裁（運用部門長）（閾値は暫定 100,000 JPY — E-08）；**買受人の変更は常に2次**。同じ価格で買受人だけを変えると差し引きは 0 になるが、金額は一人から別の人へ移るため【顧客（模擬）、2026-11-25 — #3】。REVERSE / DELTA のペアは**最も早い未締めの業務日**に記録する（PRM-120）。
   各調整行は**二つの日付**を持つ：`business_date` = 適用 / 記帳日（日次の帳簿、精算、IF-ACC-01 に使用）と `period_id` = **元取引の期**（期のお支払額 / 完納奨励金 — ADR-007 §2.3）。期は適用日では割り当てない。
   修正申請の範囲：`TRADE`（一つの取引の数量 / 価格 / 買受人）· `KANNO`（完納の再検討、常に2次 — PRM-055）· `INCENTIVE`（税率の誤りによる締め済みの期の奨励金の修正、常に2次 — ADR-006 §2.4-8a）· `LATE_ENTRY`（締め済みの日の**新しい**取引 / ロット / 引渡し — ADR-005 §2.8）。KANNO / INCENTIVE は `incentive_results` に DELTA 行を生成（`trade_adjustments` は使わない）；LATE_ENTRY は実際の取引日を持つ新しいレコードを生成。
   二つの発生源はテーブル、有効値のビュー、精算と奨励金の期への入り方を共有し、違うのは決裁の経路のみ。
3. **有効値**は、取引の元の値 + Σ 調整 でビューにより計算する；レポート、精算、奨励金は有効値のみを読む。調整は**各行の買受人**を持つので、買受人を変えても金額は正しい人に移る。
4. **取引の状態は FIG-012 に従う**。状態の変更のたびに履歴の1行（人、時刻 — PRM-114）。具体的なテーブル設計は Database Design が決める。
5. **監査：** すべての業務テーブルでトリガーが before / after を記録；スキップするフラグは**ない**、本番にリセット関数も**ない**。最初のマイグレーションは、実行者をマイグレーション用アカウントとして監査に記録する。

## 3. 検討した選択肢

| 案 | 長所 | 短所 | 結論 |
|---|---|---|---|
| **A. 追記のみ + REVERSE / DELTA、二つの発生源で一つの仕組み（採用）** | ルール4 をデータの面で満たす；プロトタイプで動作実績あり；照合 / 会計は取消仕訳に慣れている；有効値の計算は一通り | ビューの結合 → 業務日・期の範囲のインデックスが必要（ADR-009） | **採用** |
| B. その場で更新（UPDATE）+ before / after の監査テーブル | 読むのが単純 | ルール4 に反する；締め済みの日のレポートの数字が変わりうる；監査を無効にできると痕跡が消える | 却下 |
| C. 当日訂正はその場で修正し、修正申請のみ REVERSE / DELTA | 行数が少ない | 修正の方法が二つ → 計算も二通り；日中に修正された取引は買受人にとっての履歴が消える（取引確認票は既に印刷済み） | 却下 |
| D. フルのイベントソーシング（CQRS、イベントから状態を再構築） | 完全な履歴 | この件数と体制には重すぎる；レポートはプロジェクションを経由する；スケジュールのリスクが増える | 却下 |
| E. 双方向の時間を持つテーブル（有効時間 + システム時間） | 「その時点で何が見えていたか」を追える | クエリが複雑；PostgreSQL は標準で非対応；必要性は A + 監査で足りる | 却下 |

## 4. 結果

**良い点**
- 締め済みの日・期のレポートの数字は決して変わらない；差異は適用日・適用期に表示される。
- 窓口での当日訂正は素早く、かつ履歴も残る。

**悪い点 / リスク**
- 行数は修正の回数に応じて増える（この件数では無視できる）。
- エンドユーザーは「適用日」≠「元取引の日」/ 元の期を理解する必要がある → 取引の詳細画面と SC-08-03 で両方を表示。

**派生する作業**
- Database Design（`ADJUST_DB.md`）：列 `adjustment_source`、`period_id`、`correction_scope`（4値）、`buyer_changed`、買受人ごとの閾値；取引の状態履歴；seeding のフラグ / リセット関数を削除。
- 技術設計 訂正（SC-04-05）と修正申請（SC-08-03）。
