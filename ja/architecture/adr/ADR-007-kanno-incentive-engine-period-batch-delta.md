# ADR-007 — 完納奨励金のエンジン: 期ごとに決定的に計算、期ロックで凍結、締め後の修正は後の期の DELTA

| 状態 | 日付 | 決定者 | 置換 |
|---|---|---|---|
| **Accepted**（§6 の顧客待ちの点を除く） | 2026-11-26 | 受講者（L4-D09）、PL が提案 | — |

## 1. 背景

- 完納奨励金（支払期限内に全額を支払った人への奨励金）は BR-INC-01 / B.5 に従う：税係数 **110/100**、JPY の切り捨て、猶予なし、JST / 業務日基準；期限超過 = 0；締め後の修正は**後の期の差分**。テストベクタ INC-EDGE-01..03（C.3）。BR-INC-01 は修正を会計年度で**制限しない**。
- LAB-1 で計算方法は確定済み（DEC-011, DEC-012, PRM-040..043, PRM-053）：参加者の種類ごとの **2つの税率表**；区分は **適格金額（税抜）** で引く；完納の基準値 = システムが計算する期のお支払額（人 × 期 × 税率で一回計税）；期ロック時に税の端数調整の行を会計バッチへ；古い期の差分は**その期のバージョン**で再計算、完納は遡及しない；負の差分は会計年度末まで繰り越す（PRM-043 (c)）；消込が遅れた場合は、2次決裁を経て完納を再検討できる（PRM-055）。
- 入金の期への割当（L4-A04 (2)）：期 = **元取引の業務日**の月（`trades.trade_date` — ADR-005 §2.8）；支払期限後の入金は古い期に割り当てるが、その期は完納にならない；請求番号がない間は FIFO（E-02）；期ロック画面には、どの期にいくら割り当てられたかを表示（OPEN-L4-02）。
- プロトタイプは金額の部分で乖離（重大度：高）：税率表が1つ（D01）、税込額で区分を引く（D02）、入金を日付の窓で割当（D03）、税率1つ、端数調整なし（D04）、支払期限が10日固定（D05）、負の差分が繰り越されない（D23）。プロトタイプが**正しく行っている**2点は to-be でも保つ必要がある：ロック済みの**すべての期**を、ロック中の期より前に再計算（0023 `compute_incentive_rows`）、期を**元取引の日**で割り当て（0022 `period_buyer_amounts`）— 乖離表 N15, N16。
- 件数は小さい：約100–170人の参加者 × 1期 / 月。

## 2. 決定

### 2.1 純粋関数、二つのステップ

1. **純粋関数、DB 内で決定的：** 同じ入力（期に割り当てた有効な取引、入金の割当表、期の規則のバージョン、カレンダー、決裁済みの修正申請 KANNO / INCENTIVE）→ 同じ結果。時計は読まない。この件数では一つのトランザクションで同期的に実行（数秒）— 専用のバッチ基盤は不要。
2. **二つのステップ、中間の状態はない：**
   - *試算*（業務テーブルには書かない、何度実行してもよい）：期のお支払額、期に割り当てた入金、完納 / 非完納 / **要確認**、区分、奨励金、前期の差分、そして**どの入金がどの期に割り当てられたか**を表示。試算のたびに監査ログに1行（時刻、入力のハッシュ、奨励金の合計）を記録し、遅れて届いた入金 CSV の前後と比べられるようにする【顧客（模擬）、2026-11-25 — #6】。
   - *期ロック*（照合部門長 + MFA、毎回コードを再確認 — ADR-002 §2.2）：**同じトランザクション内**で、要確認の行を確定（§2.6）、正式に計算、結果を記録（追記のみ、規則のバージョン + 入力のハッシュを付与）、期を閉じ、IF-ACC-01 バッチ用の端数調整の行を生成、結果メールを outbox に積む。一つの期は一度だけロックする。プロトタイプの「計算して記録」のステップは削除（N13）。

### 2.2 計算式（詳細は完納奨励金の技術設計）

3. 期のお支払額 = 期に割り当てた税抜金額の合計（`trade_date` が期内の取引 + 期を `period_id` とする REVERSE / DELTA で、**期がロックされる前**に記録されたもの）を税率ごとに集計し、人 × 期 × 税率で**一回だけ**税を計算（生鮮の水産物は食品 → 軽減税率 8%；端数処理は規則のパラメータ `TAX_ROUNDING` に従う、既定は DEC-011）。
4. 完納 = 期に割り当てられた入金のうち、受領日 ≤ 支払期限 の分が ≥ 期のお支払額。支払期限 = 翌月の10日；**銀行の休業日**に当たる場合 → **直前の銀行営業日**に繰り上げ（`PAYMENT_DUE_RULE` = `PREV_BANK_DAY`、`is_bank_open` のカレンダー）— 前提 [PL]：振込の期限は銀行の営業日基準、経理部の確認待ち（Q-ARCH-11）。
5. 区分 = 期のバージョンにおける、**参加者の種類**（仲卸 / 売買参加者）の税率表で、**適格金額 税抜**を引く。**奨励金 = floor(適格金額 × 交付率 × 110/100)**。係数 110/100 は **RFP で固定された税係数**（BR-INC-01, B.5, 13-06）で、商品の税率（8%）に関係なく同じく適用 — 前提を明記、`tax_rates` からは読まない。例：適格金額 1,000,000 × 0.9% × 110/100 = 9,900（対応する期のお支払額は税率8%で 1,080,000）。完納奨励金の IF-ACC-01 での税区分は未確定 → Q-ARCH-12（E-01, E-06 に連動）。

### 2.3 期への割当 — 二つの時間軸（C-02）

6. REVERSE / DELTA の各行は**二つの日付**を持つ：`business_date` = 業務日の**適用 / 記帳**（最も早い未締めの日 — 日次の帳簿、日次精算、IF-ACC-01 に使用）と `period_id` = **元取引の期**（書き込み関数が `trades.trade_date` から自動で入れる；ユーザーは選ばない）。
7. 元の期がまだ **OPEN** → その行は元の期の期のお支払額に入り、元の期のロック時に奨励金に反映。元の期が **LOCKED** → その行は**現在開いている期**の期のお支払額には**入らない**；DELTA のみ（§2.4）。同じ差額は一か所でしか数えない。ロック済みの期について人が支払う / 受け取る追加分は、次の期の通知に「前期以前の調整」の行として表示し、新しい期の完納判定には加算しない（回収方法：OPEN-DB-08）。
7a. **後入力（`LATE_ENTRY`）の取引は、`trade_date` の期がすでに LOCKED のときに記録 — DELTA にはしない**（Q-INC-02；顧客は「ロック時に取引がなければ完納しない」という前提に同意していない【顧客（模擬）、2026-11-25】）：書き込み関数は元の期を `FOR SHARE`（期ロックと順番に実行）で読み、`trades.incentive_period_id` = 記帳日を含む期（常に `OPEN`）を記録する。その取引は、その期の期のお支払額、完納（**その期の支払期限**で判定）、奨励金に通常の取引と同じように入る；元の期の結果はそのまま。**一つのルール**で、元の期に取引がある人もない人も同じ扱い（TV-13, TV-15）。`trade_date` / `business_date` は日次帳簿と IF-ACC-01 では変えない。請求書への載せ方：経理部 + 照合部門長の確認待ち（前提の行「前期分の後入力」）。工数 +0.5 MD。新たに入力された取引**のみ**に適用；既存の取引の修正（修正申請 TRADE）は §2.3-7 / §2.4 のまま。

### 2.4 DELTA — 再計算の範囲（C-01）

8. 期 N をロックするとき、エンジンは**締め済みのすべての期**（会計年度の制限なし）のうち、その期のロック時刻より後に入力が変わったものを再計算する：`period_id` がその期で `locked_at` より後に記録された調整、ロック後にその期へ入金を割り当て / 割り当て取消、その期に決裁済みの修正申請 KANNO / INCENTIVE。修正申請 INCENTIVE の金額は**入力に加算される値**なので、次の再計算でも打ち消されない（TV-14）。再計算は**古い期のバージョン**で行い、古い期の記録済みの合計（MAIN + それ以前の DELTA）と比べて、期 N に `DELTA`（`ref_period` 付き）の行を生成する。古い期の完納は変えない（遡及しない）— §2.5 を除く。
9. **会計年度の制限は、負の差分の段階的な相殺にのみ適用し、再計算の範囲には適用しない。** 負の差分は後の期の奨励金から、その期の会計年度末まで段階的に相殺（CARRY）；年度末に残る負の部分は `CARRY_EXPIRED` の行を記録し、RPT-07 に表示して照合部門が処理する（回収方法：Q-ARCH-08）。`CARRY_EXPIRED` は、その期の会計年度末の期の**正の**残高消込行（その人の Σ を 0 に戻す）、`ref_period_id` = 差分の発生した期；RPT-07 は残りの未回収の絶対値を表示する。
10. **会計年度をまたぐ差分：** 2028-03 期（会計年度 2027）の取引が 2028-03 期のロック後に修正された → DELTA は 2028-03 期のバージョンで計算するが、**現在ロック中の期**（例：2028-05、会計年度 2028）に記録される。CARRY と報告では会計年度 2028 に属する。締め済みの期が会計年度の新しい期に移ったからといって、スキップされることはない。

### 2.5 修正申請 KANNO と INCENTIVE — 二次決裁を経る例外

11. **KANNO**（PRM-055, FR-CORR-02）：入金が支払期限**前**に届いていたが、消込が遅れた / 誤って割り当てられた（入金明細を証拠とする）ために、期が「非完納」と判定された場合。修正申請の範囲 KANNO は**常に2次決裁**（照合部門長 → 運用部門長、MFA）。対象の期がロック済みの場合 → 次の期ロックで、エンジンが決裁結果に従い完納を変えて対象の期を再計算し、対象の期のバージョンで、`correction_id` + 理由付きの `DELTA` 行を生成する。これは「完納を遡及しない」原則の**決裁を経た例外**であり、ロック済みの期の完納を変えられるのはこの経路だけ。対象の期が未ロックの場合 → KANNO は不要、ロック前の要確認の段階で処理（§2.6）。
12. **INCENTIVE**（常に2次決裁；人 × 期ごとに、同時に待機中の KANNO / INCENTIVE は1件まで）：ロック済みの期の奨励金が、**誤った税率**（確認済みの誤ったバージョン — R-L4-01、ADR-006 §2.5）で計算されていた場合に修正する。エンジンは自分では検出できない（エンジンにとって確認済みのバージョンは「正しい」）ため、人 × 期ごとに要求が必要：修正金額 + 理由 + 参照バージョン → 次の期ロックで `correction_id` 付きの `DELTA` 行。**INCENTIVE の金額は固定**；その後、期の適格金額が変わった（TRADE / LATE_ENTRY）場合でも、税率の修正も連動して変えるべきなら、照合部門が新たな修正申請 INCENTIVE を作成する（TV-14）。

### 2.6 ロック前の要確認 —「手数料差引の疑い」

13. 買受人が振込手数料を自分で差し引いたと疑われる場合、エンジンは**自分で非完納と結論しない**：不足が `KANNO_FEE_SUSPECT_MAX_JPY`（設定ファイル — 印を付けるだけで、金額は変えない）以下で、かつ支払期限内に入金がある → **要確認**の行。照合部門長が期ロックの画面で、理由とともに 完納 / 非完納 を選ぶ → `kanno_basis = JUDGED`。既定の候補は非完納（振込手数料は買受人負担のため — FQ-02, PRM-040）。このルールは経理部の確認待ち【顧客（模擬）、2026-11-25 — #7】。

### 2.7 入金の割当、移行の期、テストベクタ

14. **入金 → 期の割当は別テーブル（追記のみ）**：既定は未払いが残る最も古い期からの FIFO；E-02 で請求番号があると回答されれば、その番号で割り当てる。入金バッチの取消 → 割当行を打ち消す。**入金日は CSV 銀行明細の入金日で判定**（`payments.paid_on`、取込日ではない）。期ロックは、業務日 > 支払期限 **かつ** 照合が「支払期限分までの入金CSV取込済」にチェック（`incentive_runs` に保存）した場合のみ；入金日が期限後のものは対象外（猶予なし）、入金日が期限内でもロック後に入力されたものは、修正申請 KANNO（§2.5-11）でのみ完納を変えられる — Q-INC-01【顧客（模擬）、2026-11-25】；銀行 CSV の到着時刻：経理部に確認。 
15. **go-live 後の最初の期と移行の2期**（DEC-005）：移行した2期の結果は締め済みの期として取り込み、go-live のバージョンを持つ → その差分は通常の期と同様に計算できる。
16. **標準のテストセットは CI で実行**：数値は `specs/system-design/database-design/INCENTIVE_DB.md` のテストベクタの節に十分にある；規則の税率表の実物で再計算（フィクスチャがそろったとき — L4-A02）：

## 3. 検討した選択肢

| 案 | 長所 | 短所 | 結論 |
|---|---|---|---|
| **A. DB 内の決定的な関数、試算は自由、正式な計算は期ロックに紐づく、締め後は全ての締め済みの期へ後の期の DELTA（採用）** | 一つのトランザクション：計算とロックの間に隙間がない；監査のために再現できる；件数が小さいためバッチ不要 | 金額のロジックが PL/pgSQL にある → DB テストは必須、慎重なレビュー | **採用** |
| B. ビューでリアルタイム計算（常に新しい数字を表示） | 計算ステップが不要 | ロック済みの期の数字が調整で変わる → BR-INC-01 とルール4 に反する | 却下 |
| C. 古い期を再計算して結果を上書き | 元の期の数字が「正しい」 | ルール4 に反する、BR-INC-01 に反する（後の期の差分）；会計は古い期を既に計上済み | 却下 |
| D. アプリ（TypeScript）でデータを読み出して計算 | 単体テストが書きやすい | 読み出しのタイミングが異なる → 整合性を自前で確保；トリガー / RLS と切り離される | 却下；SQL のベクタで単体テストを維持 |
| E. 夜間のバッチ | 自動で動く | 期を閉じるのは照合が確認した後の人の判断（CAP-HUMAN-01） | 却下 |
| F. 日付の窓で入金を割り当て（プロトタイプどおり） | 単純 | 遅延 / 前払い / 一括入金で誤る；どの期に割り当てたかが見えない | 却下（D03） |
| G. 締め済みの期のうち**同じ会計年度のみ**を再計算（バージョン 0.1.0） | 検査する期が少ない | 3月の取引を修正しても、新しい会計年度では差分が生成されない → 金額の差が誰にも見えない；BR-INC-01 は年度で制限しない；プロトタイプより劣る | 却下（C-01） |
| H. 修正を適用日の期へ割り当てる | 時間軸が一つ | 未締めの期に古い期の差分が混ざる → 完納の判定を誤る；締め済みの期が二重に数えられる（新しい請求 + DELTA） | 却下（C-02） |

## 4. 結果

**良い点**
- プロトタイプの金額の大きなずれ（D01–D05, D23）をすべて直し、プロトタイプの正しい二つの動作（N15, N16）を同じモデルに保つ。
- 監査で、どの期でも入力 + バージョンから再現できる；締め済みの期の完納を変えるには、必ず2次決裁の修正申請が伴う。

**悪い点 / リスク**
- FIFO により、完納していた人が完納を失う可能性（OPEN-L4-02）→ E-02 の回答まで、試算画面 + テストベクタで緩和。
- 会計の請求書がシステムと異なる税額を計算する場合 → 方式 B（請求額を入力）、+0.5–0.8 MM（DEC-011, E-06）。
- 確認済みの誤った税率（N1 ブランチの E-14）は、人 × 期ごとの修正申請 INCENTIVE でしか直せない → 照合の手間がかかる（R-L4-01）。

**派生する作業**
- Database Design（`INCENTIVE_DB.md`、`BILLING_DB.md`、`ADJUST_DB.md`）：`trade_adjustments.period_id`、入金の割当表、MAIN / DELTA / CARRY / CARRY_EXPIRED の結果（`ref_period`、`correction_id`、`kanno_basis` 付き）、入力のハッシュ、端数調整の行。
- 完納奨励金の**専用の技術設計**（P3）、§2.7 のテストベクタを含む；画面仕様 SC-09-04。
