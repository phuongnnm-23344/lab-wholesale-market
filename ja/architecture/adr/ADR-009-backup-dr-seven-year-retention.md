# ADR-009 — バックアップ / DR と7年保存：PITR + Multi-AZ、大阪への複製、監査テーブルを会計年度ごとに分割

| 状態 | 日付 | 決定者 | 置換 |
|---|---|---|---|
| **Accepted**（§6 の顧客待ちの点を除く） | 2026-11-26 | 受講者（L4-D09）、PL が提案 | — |

## 1. 背景

- NFR-AVL-03：RTO ≤ 4h、RPO ≤ 15分；go-live 前に、少なくとも1回の復旧訓練を実施し、議事録を残す（PRM-082）。NFR-AVL-01：営業時間 02:00–10:00 で 99.5%。
- DR-RET-01 / B.7：取引データはオンラインで7年間検索可能；保存期間満了後の物理削除は「保存期間満了後の物理削除は承認を要する」（RFP の原文のまま）；コールドストレージからの復元は二通りの記載（"最大2営業日" / "2日以内"）。
- **TBL-ATTACH-01（08-04）は証憑の種類ごとに分ける：** 受入票・取引票・照合表 → **オンライン7年**、その後は顧客の保存方針に従う；紛争の写真・証拠、引渡し、移行のリハーサル / 検収の記録 → **オンライン3年 → コールドアーカイブ、復元 ≤ 2営業日**。B.7 は簡略に「添付書類は3年間」と記す — プロジェクトは TBL-ATTACH-01 に従う。より具体的なため（前提 [PL]、Q-ARCH-07 で再確認）。版 0.1.0 では、すべての証憑を3年後にコールドへ移し、7年後に自動削除としていた — 両方の点で誤り（Gate 1 M-08）。
- NFR-PERF-01：検索は p95 ≤ 2秒。プロトタイプ：ビューが全履歴をスキャン（D24, M23）、バックアップなし（M14）。
- 7年の件数の見積もり：約1.200取引 / 日 × 約290市場日 × 7 ≈ **約2,5百万取引**。加えて調整 / 引渡し / 数量台帳が同じ桁；監査ログが最大（取引ごとに複数行、数千万行と推定）。PostgreSQL は分散システムなしで扱える。
- RFP は RTO / RPO が地域全体の障害にも適用されるかを述べていない（Q-ARCH-01）。

## 2. 決定

### 2.1 バックアップと復旧

1. **RDS Multi-AZ**：一つの AZ の障害に対応（自動フェイルオーバー約1–2分）。
2. **PITR** を有効、35日保持；トランザクションログは約5分ごとに送信 → リージョン内の RPO ≤ 15分。毎日のスナップショット（営業時間外）は AWS Backup で取得し、方針に従って保持（暫定：毎日35日 + 月末12か月）。
3. **大阪（ap-northeast-3）への複製**：RDS のバックアップを**PITR ログごと**自動複製、S3 を複製（証憑、CSV 原本）。東京リージョン全体が失われた場合：大阪に IaC でスタックを構築し、DB を直近の時点まで復元 → 目標 ≤ 4h。待機機のホットスタンバイは置かない（TCO に含めない）。Q-ARCH-01 が「はい」の場合に適用。
4. **復旧手順書**：3つの状況に対応：データの削除 / 破損（障害前の時点へ PITR、監査ログと照合）、AZ の喪失（自動）、リージョンの喪失（大阪）。go-live 前に stg で訓練し、実際の時間を計測して、議事録を残す（PRM-082）。
5. バックアップは KMS で暗号化；鍵とパスワードは Secrets Manager に置き、リポジトリには置かない（NFR-SEC-04）。

### 2.2 7年保存と性能

6. **業務データは DB にオンラインで7年保持**、別の保管庫には移さない。
7. **パーティション（会計年度ごと）は `audit_logs` のみ**：最大かつ追記のみのテーブル；7年より古いパーティションは切り離し、S3 へ書き出してから、決裁を経た手順で削除する。業務テーブルは**分割しない**（数百万行程度 — インデックスで十分）。
8. **すべての一覧 / レポートのクエリには業務日の範囲 + ページングを必須**；大きなテーブルには `(business_date, ...)` のインデックス；有効値のビューは日付範囲のパラメータを受け取る（D24 を修正）。
9. **証憑 / 写真は種類ごとに S3 に保存**（`attachments.doc_class`、オブジェクトのタグに同じ値）：
   - `RECEIPT_SLIP` 受入票 · `TRADE_SLIP` 取引票（紙伝票のスキャンを含む）· `RECONCILIATION_SHEET` 照合表 · `CORRECTION_EVIDENCE` 修正申請の証拠（前提 [PL]：確定済みの取引に紐づくため同じ扱い）→ S3 Standard / Standard-IA で**7年オンライン**。
   - `DISPUTE_EVIDENCE` 紛争の写真・証拠、引渡し · `MIGRATION_RECORD` 移行のリハーサル / 検収記録 → Standard で3年 → ライフサイクルで **Glacier Flexible Retrieval** へ（通常の復元は数時間 — DR-RET-01 の両方の読み方に対応）。
   - **自動削除のライフサイクルは置かない。** 二つの節目を分ける：`archive_after`（コールドへ移す日、3年の種類のみ）と `retention_until`（保存期限、主レコードの業務日の会計年度末から計算、アップロード日からではない — 前提 [PL]）。月次のジョブが「保存期間満了」の一覧を作成（`retention_until` に到達）→ **運用部門長が決裁 + MFA + 理由** → オブジェクトを削除する関数を実行し、`disposal_approved_by`、`disposal_approved_at`、`disposed_at` を記録（追跡できるよう、メタデータの行は残す）。決裁されなければそのまま保持。7年の種類は、7年後に顧客の保存方針に従う（Q-ARCH-07）。
10. 本番前に、7年分のデータを模したテストデータで stg の負荷テスト（PRM-083）。

## 3. 検討した選択肢

| 案 | 長所 | 短所 | 結論 |
|---|---|---|---|
| **A. Multi-AZ + PITR + 大阪のコールド複製 + 監査テーブルの分割（採用）** | マネージドサービスで RTO / RPO を満たす；追加費用は小さい；単純 | 地域全体の障害時の RTO は IaC の構築に依存 — 確実に 4h 以内とするため訓練が必要 | **採用** |
| B. 日次スナップショットのみ | 最も安い | RPO 24h — NFR-AVL-03 を外れる | 却下 |
| C. 大阪のリードレプリカ / ホットスタンバイ | リージョン障害時の RTO は数分 | DB の費用が倍、提出済みの TCO を超える；4h の要件を超える | 却下（顧客が求めれば再検討） |
| D. 全業務テーブルを会計年度で分割 | 年単位の検索が速い | 件数が少なく効果が小さい；パーティションをまたぐ外部キー / unique が複雑；REVERSE / DELTA が元の取引と異なる年に入りうる | 却下 |
| E. 2年より古いデータを別の保管庫へ移す | DB が軽い | 「オンライン7年」に反する；古い保管庫を検索する画面が必要 | 却下 |
| G. すべての証憑を3年でコールドへ、7年後に自動削除（版 0.1.0） | ルールが一つ | 取引票 / 照合表をオンラインから早く外す → TBL-ATTACH-01 に反する；自動削除は B.7 に反する（物理削除には決裁が必要） | 却下（M-08） |
| F. 監査ログを定期的に S3 Object Lock（WORM）へ出力 | 改ざん防止が絶対的 | 具体的な監査要件がまだない；追記のみ + DB の権限で FR-AUDIT-01 には十分 | 後回し。監査が求めれば改善提案 |

## 4. 結果

**良い点**
- 実際の RPO はリージョン内で約5分、リージョン喪失時の復旧経路もある。
- 期間の範囲指定が必須のため、7年間クエリが安定。専用の保管アーキテクチャは不要。

**悪い点 / リスク**
- リージョン喪失時の RTO は訓練するまで未計測 → IaC の完成が遅れると予定リスク。
- 日付範囲の指定が必須のため、一部の検索画面はデフォルトの日付フィルタが必要（画面設計で注意）。

**派生する作業**
- Database Design：`audit_logs` のパーティション、`business_date` のインデックス；`attachments.doc_class`、種類ごとの `retention_until`、`disposal_*`（`IAM_AUDIT_DB.md`）。
- LAB-5：大阪の IaC タスク、復旧手順書、訓練、7年分の負荷テスト。
