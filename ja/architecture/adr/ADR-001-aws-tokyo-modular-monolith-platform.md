# ADR-001 — To-be基盤：AWS東京マネージド上のモジュラーモノリス

| 状態 | 日付 | 決定者 | 置換 |
|---|---|---|---|
| **Accepted** | 2026-11-25 | 受講者（L4-D01）、DEC-002 に基づく | — |

## 1. 背景

- LAB-1 の提案書と TCO は、AWS東京のマネージド、顧客名義のアカウント、IaC、dev / stg / prod を前提に書かれている（DEC-002, PRM-080）。顧客が直接支払うクラウド費用の参考値は月約235,000 JPY。
- LAB-2 のプロトタイプは Vercel Hobby + Supabase free で動いている。中核ロジックは動くが、バックアップ / PITR / 監視がなく（M14）、リージョンはデフォルト、Supabase Auth と PostgREST に強く結びついている（as-built D21）。
- 固定の制約：営業時間 02:00–10:00 JST で 99.5%（NFR-AVL-01）、RTO 4h / RPO 15分（NFR-AVL-03）、業務データはオンラインで7年（DR-RET-01）、APPI とデータの国内保管（09-06）、顧客 IT がハイパーケア後に運用を引き継げること（PRM-093）。
- 負荷は小さい：5年目時点で約77人同時 × バースト2、約1.200取引 / 日（PRM-083）。部分的にスケールさせる個別の要件はない。
- 開発チームは1チーム、9か月（DEC-003）。

## 2. 決定

1. **アーキテクチャの型：** モジュラーモノリス — Next.js + TypeScript のコードベース1つ（ページ + route handler API）、PostgreSQL 1つ。RFP のデータ領域ごとにモジュール化する（ARCHITECTURE §2）。業務の書き込みはすべて、プロトタイプと同様に DB 内の関数を通す。
2. **基盤：** AWS `ap-northeast-1` 東京、顧客名義のアカウント：
   - App：ECS Fargate を ALB + CloudFront / WAF の後ろに置き、2つのAZに跨る2タスク以上。
   - Job / batch：同じイメージを使い、EventBridge Scheduler（タイムゾーン Asia/Tokyo）で ECS タスクを起動。
   - DB：**RDS for PostgreSQL Multi-AZ DB インスタンス**、PITR 有効。
   - ファイル：S3；メール：SES；シークレット：Secrets Manager + KMS；監視：CloudWatch + SaaS。
   - IaC：AWS CDK（TypeScript）— PL の提案、アプリと同じ言語。
3. **プロトタイプから維持するもの：** Next.js のコード、zod によるバリデーション、データモデル、PL/pgSQL の業務関数、トリガー。**置き換えるもの：** 認証層（ADR-002）、DB 呼び出し層（`supabase.rpc` を PostgREST 経由で呼ぶ代わりに、EXECUTE 権限のみを持つ DB ロールで関数を呼ぶ型付きの SQL クライアント）、基盤。
4. デプロイと保守は 01:00–10:00 に行わない。保守の時間帯は 20:00–24:00 または休市日（PRM-081）。

## 3. 検討した選択肢

| 案 | 長所 | 短所 | 結論 |
|---|---|---|---|
| **A. AWS東京のマネージド、モジュラーモノリス（採用）** | 提出済みの提案書 / TCO と一致；Multi-AZ、PITR、大阪へのバックアップ複製が揃う；アカウントは顧客名義 → 顧客がデータを保持；顧客 IT に馴染みのあるモデル | Supabase の Auth / PostgREST を自前で置き換える必要がある（LAB-1 の見積もりに一部含まれる）；インフラの構成要素が増える | **採用** |
| B. Vercel + Supabase の有料プラン（プロトタイプのまま） | 移行作業が最も少ない；プロトタイプは既に動く | 契約主体が SaaS 提供者名義になり、正しい顧客アカウントに置きにくい；RTO / RPO とデータの所在がプランと第三者のリージョンに依存し、監査で証明しにくい；Vercel には全構成要素を「日本のみ」にするリージョンがない；提出済みの TCO と PRM-080 に反する | 却下（L4-D01） |
| C. 中立な論理アーキテクチャ、インフラは未定 | 柔軟 | バックアップ / DR、監視、費用を設計できない；LAB-5 でインフラのタスクに分解できない | 却下（L4-D01） |
| D. マイクロサービス（領域ごとに1サービス） | スケール / デプロイを独立させられる | 負荷は小さく、チームは1つ；領域をまたぐトランザクション（取引確定でロット数量を減算 + 参加資格の検査 + 監査）は saga になる — ルール4 が禁じる不整合のリスクが、まさにこの箇所で生じる；運用コストが増える | 却下 |
| E. サーバーレス（Lambda + API Gateway） | サーバー管理が不要 | ピーク時間帯 02:15–05:00 にコールドスタート；DB 接続が多く RDS Proxy が必要；Lambda 上の Next.js は層が増えて複雑 | 却下 |
| F. RDS の代わりに Aurora PostgreSQL | フェイルオーバーが速い；ストレージが自動拡張 | 小さい負荷に対して費用が高い；RDS Multi-AZ は 1日8時間で既に 99.5% を満たす | 却下（Q-ARCH-01 で大阪のホットスタンバイが必要と判明すれば再検討） |

## 4. 結果

**良い点**
- NFR-AVL-01/03、DR-RET-01 を、計測可能で訓練もできるマネージドサービスで満たす。
- 業務ロジックが DB 内にあり基盤に依存しない → プロトタイプの実稼働の証拠を再利用できる。

**悪い点 / リスク**
- 認証（ADR-002）と DB 呼び出し層を書き直す必要がある。RLS の識別子の出所が Supabase JWT から セッション変数 `app.user_id` に変わる。
- モノリスのため、1つのメモリ障害がアプリ全体に波及しうる → 2タスク以上 + ヘルスチェック + ローリングデプロイで緩和。
- クラウド費用は顧客が支払い、USD建てのため為替変動の影響を受ける（estimate-basis §5.3 に記載済み）。

**派生する作業**
- Database Design（P2-B）：`auth.users` の代わりにアカウントテーブルを記載し、デモ用の列を削除。
- LAB-5：dev / stg / prod の IaC タスク、CI/CD パイプライン、復旧訓練（PRM-082）。
