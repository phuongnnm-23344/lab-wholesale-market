# ADR-003 — 3層の権限、DB で検査：許可と承認は表もライフサイクルも分離

| 状態 | 日付 | 決定者 | 置換 |
|---|---|---|---|
| **Accepted**（§6 の顧客待ちの点を除く） | 2026-11-26 | 受講者（L4-D09）、PL が提案 | — |

## 1. 背景

- ルール2：許可（審査付きの許可、仲卸 — 中間の卸売業者向け）と承認（届出による軽い手続き、売買参加者 — 売買の参加者向け）は、二つの異なる根拠である。一つの権限に統合する案は却下された（02-08, 12-06）。
- BR-PERM-01：資格の有効性は**取引確定の時点**で検査する。売買参加者にはさらに参加上限（期ごとの枠、既定値 = 保証金、警告のみで強制停止しない — PRM-046, L4-A04 (1)）がある。
- TBL-ROLE-01：社内ロール7つ + 画面ごとの読み書きマトリクス。プロトタイプは閲覧権限を簡略化していた（社内の全員が全件を読める — D18, M18）。
- 社内の決裁は、**決裁権限**（照合部門長 / 運用部門長 / 配送部門責任者）および期間付きの代行者が行う（PRM-129）。自分が起票したものを自分で決裁することは禁止（PRM-120, PRM-129）。
- プロトタイプは既に正しい方向のモデルを持つ：二つのテーブル `nakaoroshi_permits` / `baibai_approvals` と種別を検査するトリガー；すべての RPC に `assert_caller(roles, authorities)`（as-built §2.3, §2.5）。

## 2. 決定

1. **三つの層を分離**（ARCHITECTURE §5）：
   - *社内ロール* — TBL-ROLE-01 の7つのロール、アカウントに紐づく。**一人が複数のロールを持てる**（受付と目利きを兼ねる人、照合とルール管理を兼ねる人など）。一人一アカウント（PRM-089）、ロールの付与・解除は履歴に残す。職務分掌（SoD）は**人**単位で検査する（項目4）ため、兼任があっても自己決裁の抜け道にはならない。前提 [PL]、OPEN-DB-10 待ち。
   - *決裁権限* — 三種類、アカウントに紐づき、付与・解除の履歴がある。**代行**は開始日・終了日を持つレコードで、期限が来ると自動的に失効する。
   - *参加資格* — 参加者に属する（アカウントではない）：許可、承認、卸売業者の市場登録、買出人の拠点での登録。
2. **許可と承認：二つの表、二つのライフサイクル、二つの手続き。** 状態は FIG-010（有効 / 一時停止 / 失効 / 再審査）に従い、追記のみの履歴として記録する。更新 ≠ 再審査（PRM-121）。トリガーが誤った種別の参加者への紐付けを阻止する。**「許可と承認を一つにまとめた」汎用の表や enum は作らない。** 画面 SC-01-02 は二つの独立したブロックを表示し、資格の状態は**各ブロックの中**に表示する（L4-D02）。実際の違い（LAB-4 の課題：「審査付きの条件が必要な種別」と「より軽い承認手続きで足りる種別」）：

| | 許可 (仲卸) — 条件付きの審査 | 承認 (売買参加者) — より軽い手続 |
|---|---|---|
| 新規 | **照合事務局**が入力 → **審査**（結果 + 許可の条件、イベント `REVIEWED`）→ 照合部門長が起案 → **運用部門長が決裁 + MFA**（前提 [PL]） | 届出：照合事務局が入力 → **照合部門長が確認 + MFA**。保証金 / 資力の条件を軽く確認（一人） |
| 通常の更新 | **PRM-121：** 照合事務局が入力 → **照合部門長が確認 + MFA**。許可の条件を見直したことを記録。再審査はしない | 左と同じ（PRM-121） |
| 独自の項目 | 許可番号、**許可の条件**、審査の結果 / 日付 | **参加上限**（既定値 = 保証金）。変更は `LIMIT_CHANGED` イベント（旧 / 新 / 理由）でのみ — **上書きしない** |
| 取引確定時の検査 | 許可が有効 | 承認が有効 + 期ごとの参加上限の警告（相対 + せり） |
| 一時停止 / 失効 / 回復 | 照合部門長が起案 → 運用部門長が決裁 + MFA（PRM-121）。弁明の機会があるか → OPEN-DB-09 | 左と同じ（PRM-121） |
| 失効日を過ぎた場合 | `EXPIRED` を自動設定 — 前提 [PL]：FIG-010 は 有効 → 失効 の直接の遷移を描いていない | 左と同じ |

   各段階の決裁者は PRM-121 に基づく前提 [PL]。運用部門が OPEN-DB-09 で確認する。
3. **DB でも検査する。アプリだけに頼らない：** すべての書き込み関数は `assert_caller(vai, quyền duyệt)` を呼び、`app.user_id`（ADR-002）と、`now()` 時点で有効なロール / 権限 / 代行のテーブルを参照する。取引確定の関数は、買受人の資格の検査を、ロットの数量を減算するのと**同じトランザクション内**で行う：仲卸 → 許可が有効；売買参加者 → 承認が有効 + 期の参加上限を計算（相対 + せりを合算）；それ以外 → 理由付きで拒否（FR-AITAI-02）。
4. **職務分掌（SoD）をデータ制約で担保：** 決裁者 ≠ 起票者；同一の修正申請の1次 ≠ 2次；配送紛争の確認者 ≠ その引渡しの記録者；規則の maker ≠ checker；入金バッチの取消者 ≠ 取込者。関数内で検査し、標準のエラーコードを返す。
5. **閲覧権限：** RLS はロール × 画面のマトリクス全体に従う（L4-A06）。マトリクスは**一度だけ**データの表として書き（表名は Database Design で決める）、RLS のポリシーと UI のメニューはそこから読む — 二か所に手で写さない。
6. 用語：画面と文書の社内の決裁には 決裁 / 確認 を使い、承認 は使わない（PRM-121）。

## 3. 検討した選択肢

| 案 | 長所 | 短所 | 結論 |
|---|---|---|---|
| **A. 三層、許可 / 承認は二つの表、DB で検査（採用）** | データの面でルール2を満たし、画面だけでの対応ではない；資格の検査と数量の減算が同じトランザクション内にあり、二回の検査の間の隙間がない；プロトタイプで動作実績あり | 二つの表はほぼ同じ構造 → CRUD のコードが重複；閲覧マトリクスのためのデータ表が別途必要 | **採用** |
| B. 種別の列を持つ一つの `qualifications` 表 | 表が少ない | 「一つの汎用の権限」になりがち；参加上限のような固有項目が NULL 許容の列になる；レビュアーがスキーマで統合を見ると、ルール2違反として却下されるリスク | 却下 |
| C. アプリ層（ミドルウェア）だけで権限を検査 | 慣れている | DB への直接呼び出し（スクリプト、ジョブ、コードの不具合）が迂回できる；BR-PERM-01 は確定のトランザクション内で検査する必要がある | 却下 |
| D. 外部のポリシーエンジン（OPA / Cedar） | 宣言的なポリシー | 運用コンポーネントが増える；ルールは業務データ（有効性、期ごとの上限）に強く結びつくため、結局 DB を参照する必要がある | 却下 |

## 4. 結果

**良い点**
- ルール2 がスキーマ、取引確定の関数、画面の三か所に現れ、三者が揃う。
- 代行 + SoD により、アプリにバグがあっても DB レベルで自己決裁を防ぐ。

**悪い点 / リスク**
- 業務ロジックが PL/pgSQL にある → DB のテスト標準が必要（プロトタイプの 11 本の検証スイートを基礎にできる）。
- 役割 × 画面の閲覧マトリクスにより、RLS がプロトタイプより複雑になる。否定テスト（ロールが読めてはいけないもの）が必要。

**派生する作業**
- Database Design：ロールの表（`staff_roles`、一人複数ロール）、決裁権限、代行、閲覧マトリクス（`IAM_AUDIT_DB.md`）；許可の状態履歴（`REVIEWED`）/ 承認の履歴（`LIMIT_CHANGED`）、保証金の履歴（D14）（`PARTY_DB.md`）。
- 仕様：SC-01-02 の二つのブロック；SC-02-03 の代行者タブ（PRM-129）。

§2 の決定は **Accepted**（L4-D09）。以下の点は顧客の実際の回答をまだ待っている。回答は表の値や分岐を変えるだけで、ADR の方向性は変えない。方向性を変えるなら新しい ADR で置き換える。ADR 内の `[Customer giả lập]` を含む文は、根拠のある前提であり、顧客の実際の確認は `project/02_requirements/qa.md` と合わせて行う。

| ID | 顧客回答待ちの点 | 現行設計（前提） | 顧客の回答が異なる場合 | 回答者 |

| OPEN-DB-09 | 許可と承認の新規発行 / 停止の手続き。弁明の機会はあるか（更新は PRM-121 で確定済み） | [PL] 許可：審査 + 運用部門長が決裁。承認：届出 + 軽い審査 + 照合部門長が確認。停止は両方とも：運用部門長が決裁 | ライフサイクルの関数で各段階の決裁者を変更。表の分離、ライフサイクルの分離は変えない | 運用部門 |
