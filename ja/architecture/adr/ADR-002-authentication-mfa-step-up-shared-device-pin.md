# ADR-002 — Supabase Auth に代わる認証：サーバー側セッション、MFA step-up、共用端末のPIN

| 状態 | 日付 | 決定者 | 置換 |
|---|---|---|---|
| **Accepted**（§6 の顧客待ちの点を除く） | 2026-11-26 | 受講者（L4-D09）、PL が提案 | — |

## 1. 背景

- プロトタイプは Supabase Auth（メール + パスワード）、`auth.uid()`、`banned_until` を使用。MFA はなし。担当者の切替は PIN がオンラインのときのみ可能（as-built D17, D21；M02, M03）。AWS へ移行（ADR-001）すると、この層を置き換える必要がある。
- NFR-SEC-01：管理者および決裁権限者には MFA が必須。LAB-1 で提案した解釈（PRM-113、E-15 待ち）：決裁権限者は通常は社員番号 + PIN で作業し、決裁 / 機微なデータの出力の**直前に** MFA を求める（step-up）。対象操作の一覧は PREMISE §3.2。
- 現場：シフト制の共用端末、手袋をはめて使う、一人一アカウント、ログインの使い回しは禁止（PRM-089）。4桁の PIN で数秒で担当者を切替。タイムアウトは受付のPCで約30分、岸壁のタブレットで約5分（PRM-112）。
- 顧客の想定（FB-CUS-229, 230, 231）：MFA の有効時間は10–15分、同じ人・同じ端末に限り、担当者が変わったら無効。SYS-ADMIN はログイン時点で MFA。**会社は携帯電話を支給しない**ため、個人の携帯を使いたくない人がコードを受け取る方法が必要で、決裁権限者が他人の端末を借りないようにする。
- MFA が必要な人数：約12–13人（照合部門長、運用部門長、配送部門責任者、代行者、管理者）（PRM-088, E-15）。

## 2. 決定

### 2.1 識別子とセッション

1. モジュール `iam` が PostgreSQL 内でアカウントを自ら管理する（`auth.users` の代わりのアカウントテーブル）。パスワードは argon2id でハッシュ化。自由登録はない。
2. **サーバー側セッション**を DB に保存（Cookie は `HttpOnly`、`Secure`、`SameSite=Strict`、ランダムな ID）。即時に無効化できる（アカウント停止 → セッション削除）。`banned_until` はアカウントの状態 + 履歴に置き換える（FR-IAM-02）。
3. **共用端末の二層：**
   - *端末*：端末を登録する（端末 ID は SYS-ADMIN が発行）。権限のあるアカウントで、シフト開始時に一度だけ端末にログインする。
   - *ユーザー*：社員番号 + 4桁の PIN で担当者を切替。使用中の人の名前をすべての画面に表示する。端末種別ごとのタイムアウト（設定ファイル — PRM-126）で担当者切替の画面に戻し、入力中のデータは保持する。
4. DB に書き込むすべてのトランザクションは、`set_config(..., true)` で `app.user_id`、`app.device_id`、`app.mfa_verified_at` を設定する — 関数 `assert_caller` と RLS はここから読む（`auth.uid()` の代わり）。

### 2.2 MFA

5. **Step-up** は PREMISE §3.2 の操作の前に行う（修正申請の決裁、日次締め、期ロック、配送の紛争の確認、規則の確認 / ロールバック、参加者資格の変更、会計 CSV / 個人データ / 監査ログの出力、他人の PIN のロック解除）。
6. **有効時間：10分**。（人、端末、セッション）の組に紐づく。PIN による担当者切替、タイムアウト、ログアウトのいずれかで直ちに無効。10–15分の範囲で低めを選んだ理由は、共用端末が人の多い場所にあるため。値は設定ファイルにある。
6a. **step-up はアイドルが3分を超えると無効**（設定ファイル）。PCのセッションのタイムアウト（約30分）は MFA の有効時間より長いため、MFA を済ませた人が席を離れた後、残りの10分の間に他人が決裁を押せてしまう。**取り消せない操作は、step-up が有効でも必ずコードを再確認する**：日次締め、期ロック、規則の決裁 / ロールバック、証憑の物理削除の決裁。
7. SYS-ADMIN のアカウント：ログイン時点で MFA を要し、上記の通り10分後に step-up を再度要する。
8. **方式（利用者の優先順位順。各自が少なくとも一つ登録する）：**

| # | 方式 | 対象 | 備考 |
|---|---|---|---|
| a | 個人の携帯のTOTPアプリ | 個人の携帯を**自発的に**使う人 | 必須ではない；会社は携帯を支給しない |
| b | **TOTP ハードウェアトークン（OATH、数字表示付きのキーホルダー型）** を個人ごとに配布 | **個人の携帯を使わない人**（FB-CUS-231） | 顧客が購入（PRM-088）；配布時に一つのアカウントに紐づける；トークンの保管は印鑑を持つのと同じ；タブレットでも PC でも使える。6桁を入力するだけで、USB / NFC ポートは不要 |
| c | SYS-ADMIN が発行する**使い捨ての予備コード**（管理者の MFA、監査あり）、当日中に期限切れ | 紛失・忘れたときの予備 | メールの OTP は使わない：メールボックスはその PC で既に開いているため、要素が一つ残ってしまう。担当の管理者がいない場合は **代行者** に業務を任せる |

9. **他人の端末を借りない：** コードは、そのコードを保有するアカウントにのみ有効。「共通のコード」やグループ向けのコードは作らない。トークンを紛失 → SYS-ADMIN が直ちに失効させ（管理者の MFA、監査あり）、IT 部門の金庫から予備のトークンを発行する。その間の決裁は **代行者**（PRM-129）に任せ、MFA は緩めない。
10. 最初の MFA 方式の登録、および方式の変更は、事務所の PC で行い、SYS-ADMIN が確認し、監査に記録する。

### 2.3 ロックと記録

11. PIN を5回誤る → 15分ロック。人単位と端末単位の**両方**でカウントする（M22 を修正）。パスワードや MFA コードを複数回誤った場合 → 一時ロック ＋ セキュリティイベントを監視へ送る（NFR-SEC-03）。
12. 夜間の PIN のロック解除 / 再設定：運用部門長または配送部門責任者が、MFA を用いて行う（PRM-111, PRM-112）。
12a. **ハードウェアトークンのライフサイクル**（IT の運用手順、Q-ARCH-03）：TOTP のシードを KMS 経由で投入（平文で保存せず、メールで送らない）；時刻のずれを同期（±1ステップの許容、認証時にずれを計測）；トークンの電池は約3–5年、システムは7年稼働するため、ロット単位の交換計画を立て、交換費用を顧客に伝える。
12b. **ルール管理者（交付率表の maker）は NFR-SEC-01 の「管理者アカウント」に当たるか** — 当たる場合は SYS-ADMIN と同様にログイン時点で MFA。E-15 に回す。暫定の前提：当たらない（maker は単独でバージョンを有効化できず、checker は MFA を持つ）。

### 2.4 外部の参加者

13. 第1期では外部の人のアカウントは**ない**（L4-A08）。第2期向けのポリシー SEC-IAM-02：ログインごとにメールの OTP、独立したレルム（ARCHITECTURE §10）。コンプライアンス上は「一部対応」と記載。

## 3. 検討した選択肢

| 案 | 長所 | 短所 | 結論 |
|---|---|---|---|
| **A. アプリ + DB 内で `iam` モジュールが自ら管理（採用）** | アクションごとの step-up、PIN による担当者切替、端末への紐付け、ハードウェアトークン — いずれも、どの IdP を使うかに関係なく自前で書く流れ；監査の場所が一つ；`set_config` による DB への識別子の受け渡しが単純 | パスワード / セッションの安全性を自分で担う → 検証済みのライブラリを使う（argon2、TOTP RFC 6238）、セキュリティレビュー、本番前の侵入テスト | **採用** |
| B. Amazon Cognito | マネージド、ソフトウェア TOTP あり | 共用端末での PIN による担当者切替がない；アクションごとの step-up はカスタム認証フローで自作が必要；ハードウェア TOTP トークンは標準では非対応；DB の権限表と同期すべき ID の保管場所が一つ増える | 却下 |
| C. 顧客の企業 IdP（Entra ID など）を OIDC 経由で | 事務所の PC の SSO | 顧客が持つか不明（Q-ARCH-10）；岸壁の共用端末の問題は解決しない；システム範囲外の外部依存 | 第1期では却下。顧客が持つなら料金を分けた改善とする |
| D. SMS の OTP | 馴染みがある | 携帯電話が必要 — 顧客に携帯がないところ；BR-NOTIFY-01 で SMS は既に除外 | 却下 |
| E. FIDO2 セキュリティキー / パスキー | フィッシングに最も強い | 現場のタブレットが未選定（E-05）、タブレットのブラウザの USB / NFC 対応は不確か；手袋が濡れている | 第1期では却下。端末確定時に再検討 |
| F. 決裁者全員に毎回のログインで MFA | 単純 | 決裁者も現場で作業し、シフト中に担当者切替が何度もある → 受付カウンターが遅くなる；顧客は step-up を尋ねている（PREMISE §3.2） | 却下。ただし E-15 が要求した場合は別（±0.1–0.2 MM、L4-A07） |

## 4. 結果

**良い点**
- NFR-SEC-01 を、PRM-113 の解釈で、受付カウンターを遅くせずに満たす。
- 個人の携帯を持たない人にも専用の方式（トークン）がある — FB-CUS-231 を解消。

**悪い点 / リスク**
- 顧客がトークンを購入して管理する（約12–13個 + 予備）。配布 / 回収 / 電池交換の手順が必要（Q-ARCH-03, §2.3-12a）。
- 認証を自前で書く → セキュリティテストが必須（SCOPE-06 の範囲に既に含む）。
- E-15 が「毎回のログインで MFA」と答えた場合 → ログインの流れを変更、±0.1–0.2 MM。

**派生する作業**
- Database Design：アカウント、セッション、端末、MFA 方式（暗号化された secret）、ロックの履歴のテーブル。
- 仕様 SC-00-01 / SC-00-02（ワイヤーフレーム）、決裁を行う各画面に step-up の箇所を明記。
- IT の運用手順書：トークンの配布 / 失効、MFA の再設定。
