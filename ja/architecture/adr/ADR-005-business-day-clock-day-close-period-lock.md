# ADR-005 — 業務日、日次締め、期ロックの時計：DB レベルでロックし、再開しない

| 状態 | 日付 | 決定者 | 置換 |
|---|---|---|---|
| **Accepted**（§6 の顧客待ちの点を除く） | 2026-11-26 | 受講者（L4-D09）、PL が提案 | — |

## 1. 背景

- 業務日は暦の日付と一致しない：ロットは 01:00（ロット受付時刻 — 規則のパラメータ、E-16）から受け付けられ、その朝の業務日に属する；取引の確定は 02:00 から（PRM-116）。バージョン 0.1.0 では**二つの定義**があった（取引は 02:00 → 01:59、ロットは 01:00 から）。そのため日を開くジョブが 02:00 に動くと、01:00–02:00 のロットを記録する OPEN な業務日がなかった（Gate 1 M-01）。
- 期（支払期間）＝ **元取引の業務日**に基づく暦月（L4-A04 (2)）。
- BR-CLOSE-01：締め済みの日は直接修正しない。締め後の修正は、修正申請で最も早い未締めの日に入る（PRM-120）。期ロック後の修正は翌期の差分に入る（BR-INC-01, ADR-007）。
- 締め済みの日への遅れて届いたレコード（紙伝票の後入力、オフラインの遅延同期）や、一台の故障 / 紛失した端末のためにチェックリストが止まる恐れがある（Gate 1 M-05；【顧客（模擬）、2026-11-25 — #1】）。
- プロトタイプ：`current_business_date()` = 最大の OPEN 日、ジョブなし、02:00 前のロットは紐づかない（D22, M10）。LOCKED 日への書き込みをブロックするトリガーは正しく動いていた。

## 2. 決定

1. **カレンダーが正：** 市場・銀行カレンダー（SC-10-05）が、市場の開場日 / 休市日 / 臨時休市 / 臨時開市、および銀行の営業日を決める。臨時休市 / 臨時開市は当日中に変更でき、受注者の手配は不要、規則のクオータにも数えない（FB-CUS-239）。
2. **業務日の定義は一つ：** 業務日 D = **[D 01:00, D+1 01:00) JST**の期間。01:00 は有効な規則バージョンの `LOT_INTAKE_START_TIME`。取引の確定は `TRADE_START_TIME`（02:00、PRM-116）からのみ可能。「01:30 に確定した取引は前の日に属する」というケースは無い — 02:00 前には取引を確定できない。
3. **業務日はサーバーで割り当てる**。端末の時計は使わない：関数 `business_date_for(t)` = （t − `LOT_INTAKE_START_TIME`）の日付。ロット、取引、引渡し、期、年間クオータで同じ関数を使う。オフラインのレコードは端末の時刻とサーバーの受信時刻の両方を持つ；業務日は同期時にサーバーが決める（ADR-008）。
4. **業務日を開く：** 日次締め関数は、日 D の締めで**カレンダー上の次の市場の業務日を開く**（OPEN、`intake_opens_at` = その日の 01:00）→ 修正申請 / 後入力の午後の決裁のために、常に「最も早い未締めの日」が存在する。**`LOT_INTAKE_START_TIME`（01:00 JST、EventBridge Scheduler のタイムゾーン Asia/Tokyo）のジョブ**は安全網：日が無ければ開く（冪等）。ジョブが失敗したらアラーム；権限者は同じ関数を手動で実行できる（監査あり）。
5. **日次締め：** 照合部門長（または代行）+ MFA（毎回コードを再確認 — ADR-002 §2.2）。PRM-119 のチェックリストが全て表示された後。締め = 日のステータスを変更 + トリガー `DAY_LOCKED` が、その日のすべての業務テーブルへの書き込みを拒否。数量の残るロットは、ロットコードの後ろに付けて翌日へ**持ち越し**（PRM-110；E-12 待ちの暫定ルール、規則と同様に扱う）。**標準のチェックリスト**（SC-07-02 はこの一覧を正確に表示）：

6. **締めが止まったときの逃げ道 —「端末回収不能」：** 故障 / 紛失 / 電池切れの端末は同期できない → 照合部門長（または代行）が、端末に「端末回収不能」を理由 + MFA + 監査付きでマークする。端末はチェックリストの項目3から外れ、その端末のセッションと オフライン PIN は無効化される；その端末のレコードが後で届いた場合 → SC-03-07（要確認）→ 項目8 の後入力の経路。紙からも完全に失われた分は、項目8 に従って後から入力する。
7. **締め済みの日を再び開く機能はない**（Q-ARCH-02 — Expert Gate 1 は維持に同意）。誤って締めた / 漏れがあった場合 → 修正申請、または後入力（項目8）で、最も早い未締めの日に入れる。
8. **締め済みの日に遅れて届いたレコード（後入力）：** 締め済みの日に**新しく**発生した取引 / ロット / 引渡しは、その日には記録しない。**修正申請の範囲 `LATE_ENTRY`** に入る：新しいレコードの内容 + 元の日付 + 証拠（紙伝票のスキャン）；照合部門長が決裁（閾値以上なら2次）。決裁後、開いている業務日（`business_date` = 記帳日）に、**実際の取引日**を別に持って記録する（`trades.trade_date`、`deliveries` / `lots.original_business_date` = 元の日付）；期は元の日付で決まり、ADR-007 §2.3 の OPEN / LOCKED のルールに従う；ロック済みの期の新しい取引は、現在開いている期で期のお支払額 / 完納 / 奨励金を計算（`trades.incentive_period_id` — ADR-007 §2.3-7a、Q-INC-02）。ADR-008 と SC-03-07 も同じ経路を使う。
9. **期ロック：** 支払期限 + 照合の時間の後；照合部門長 + MFA；同じトランザクション内で完納奨励金を正式に計算し、結果を凍結（ADR-007）。ロック後に、その期に割り当てられた変更は翌期の DELTA になる；完納を遡及して変えない（例外として決裁あり：修正申請 KANNO — ADR-007 §2.5）。
10. **IF-ACC-01 の出力** は日次締め後に作成し、作成時点の内容を凍結する（PRM-123）。

| 案 | 長所 | 短所 | 結論 |
|---|---|---|---|
| **A. カレンダー + 次の日を締め時に開く + 01:00 の予備ジョブ + DB で永久にロック + 後入力は修正申請で（採用）** | BR-CLOSE-01 をデータの面で満たす；業務日は一つの関数で決まる；月初の01:30のロット、3/31→4/1 の境界をテストできる；遅れたレコードは決裁の経路が明確 | 再開できない → 締めの誤りは修正の経路で対応 | **採用** |

| D. 業務日 = 暦の日、02:00 前のロットは前日扱い | 単純 | 実態と異なる：01:00 に受け付けたロットはその朝の業務日；期の奨励金が境界の日でずれる | 却下 |

| G. 締め済みの日への後入力を、決裁なしで開いている日へ直接記録（0.1.0） | 速い | 取引の業務日が誤って別の期へ入る；伝票と取引日がずれる；決裁者がいないまま BR-CLOSE-01 を回避 | 却下（M-05） |

## 4. 結果

**良い点**
- 一つの業務日の関数をロット、取引、期、年間クオータで共有 → 境界の日付は共通のテストベクタを持つ（ADR-007 §2.7 TV-09）。
- 一台の故障した端末がチェックリストを止めない；遅れたレコードは決裁者がいて、実際の取引日を保持する。
- 管理者を含め、誰も締め済みの日の数字を変えられない。

**悪い点 / リスク**
- 次の日は日次締め関数が開く；前の日がまだ締まっていなければ 01:00 のジョブが開く。ジョブが失敗し、かつ前の日が未締めだとロットを受けられない → 即アラーム + 手動で開く関数；01:00–10:00 はデプロイしない。
- 「端末回収不能」は、チェックリストを通り抜ける近道 → 照合部門長 / 代行のみ、理由 + MFA を必須にし、日次締めのレポートに表示する。
- 締め間違いは元に戻せない → チェックリスト + MFA が止めの役割を果たす。

**派生する作業**
- Database Design：カレンダー、日・期のステータス、締めの履歴（`CLOSE_DB.md`）；`trades.trade_date`、`*.original_business_date`、`devices.lost_*`、`trade_fixes.reviewed_*`、`delivery_exceptions.settle_reviewed_*`、`correction_scope = LATE_ENTRY`。
- 仕様 SC-07-02（日次締め）、SC-09-04（期ロック）；ワイヤーフレーム SC-10-05。
