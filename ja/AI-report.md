## 2. AIの体制とプロンプトの書き方

### 2.1 役割を3つに分け、一人が調整する

私は一つのAIセッションで全部を任せることはしなかった。プロジェクトには役割が固定された3つのエージェントがある（定義は workspace の `.claude/agents/` にある）:

| 役割 | 役割 | 禁止事項 |
|---|---|---|
| **Project Leader (PL)** | PREMISE、アーキテクチャ、ADR、DB、ワイヤーフレーム、spec、スクリプトなど全成果物を作成; feedback に基づき修正; feedback / 決定 / 顧客への質問を記録 | 自分の成果物を自分で採点すること、顧客の代わりに自分で回答すること |
| **Expert reviewer** | 各ゲートで受講者が指示した基準に沿って採点し、verdict（RELEASE / 条件付き RELEASE / RELEASE 不可）を出す | PLの成果物を修正すること |
| **顧客（模擬）** | 桜水産市場とエンドユーザーの役を演じる: 質問に回答し、ワイヤーフレーム / 前提に意見を出す | RFP以外の回答には `[Giả lập]`（日本語版では【模擬】）を付けること |

メインのチャットセッションは **調整のみ** を行う: 作業を適切な役割に渡し、役割の間で結果を受け渡し、受講者に報告する。理由: AIが自分の書いた文書を自分でレビューすると、多くの場合は自分が正しいと思っていたことを再確認するだけになる。書く人と採点する人を分けると、誤りがより多く表に出る（Gate 1 では、PLが自分で確認しても見えなかった Critical 2件を検出 — 3節）。

PLは毎回、`CLAUDE.md`（課題の不変の7つのルール）を読み、RFPを要約し、作業メモ `pl-memory.md` と feedback 簿を確認して始める; 最後にメモ + ファイル一覧 + 顧客への質問を更新して終える。そのため、AIのセッションはそれぞれ最初から始まるが、複数セッションにまたがっても流れを失わずに作業できる。

### 2.2 作業依頼プロンプトの書き方

- **範囲と基準を明確にし、結果は形式を固定する。** PL向けのプロンプトには常に次を含める: 作業内容、修正してよいファイル、読むだけのファイル、完了の基準、最後の報告の形式（変更したファイル · index に追加する行 · 新しいエラーコード · 新しい質問 · 見つかった矛盾 · `Status`）。Expert向けのプロンプトは、各ゲートで受講者が範囲と基準を指定する（LAB-4の学習目標 + RFP + 7つのルール + spec-standards）。
- **並行実行の前に共通ブリーフを作る。** P3（spec）とワイヤーフレームHTMLは、同時に動く3つのAIの流れに分けた。共通ブリーフのファイルを毎回作る（`p3-shared-brief.md`、`wireframe-html-shared-brief.md`）: 背景、文書の基準、必須の内容、言語、**ファイルの所有権**（どの流れがどのファイルを修正するか、共通ファイルはPLだけが統合）、コミット禁止。各流れのプロンプトには、その流れの画面の範囲だけを追加した。
- **共通の決定は修正の前に書く。** Gate 1 の修正では、決定 D1–D13 のブリーフ（業務日の定義、締め済みの期の再計算の方法、日次締めのチェックリスト…）を作り、同期が必要な5箇所（PREMISE、ADR、DB、ワイヤーフレーム、テストベクタ）の唯一の出典とした — メモ (4) は `AI-report-evidence/logs/progress-lab4-ai-report-notes.md` を参照。
- **未確定の点はAIに推測させない。** 顧客が回答していない事項は、質問 + 仮の前提 + 誤った場合の影響（ルール7）として `qa.md` に書く; 顧客（模擬）が回答した場合は、出典ラベル付きの前提として使い、確定事項のように書かない。

## 4. 特記事項と自己評価

### 4.1 効果があったと考える点

- **書く人 / 採点する人 / 受講者を分けた。** 役割を3つに分けたことで誤りが早く表に出た: Gate 1 の Critical 2件は、PLが自分で確認しても見えなかった誤り。Gate 1 では finding 23件、Gate 2 では 13件、Gate 2 完了では Minor 8件まで減った; Gate 3（提出一式全体）では Critical 0件、Major 3件はすべて提出に添付する文書とリポジトリのセキュリティにあり、設計の内容にはなかった。
- **並行実行では共通ブリーフとファイル所有権を分けた。** Gate 1 の修正以降、流れの間で書き込みの衝突はなくなった; 残った矛盾はすべて *規約の欠如* によるもので、互いに上書きしたためではない。
- **独立した記述し直しで検査する**（パリティ確認）。書いた本人に確認させるのではなく — 読み直しても見えなかったずれを検出できた。
- **一つの出典 → 一つのコマンドで複数の出力**: ワイヤーフレームHTMLから PDF + PNG + spec画像を生成; Mermaid から PNG を生成。ワイヤーフレームを変えても手描きし直す必要はなく、画像の番号は常に ID 列と一致する。
- **未確定の点はすべて、見積への影響を伴う質問にする**（ルール7）。模擬の回答にはすべて出典ラベルを付け、読者はどこが決定で、どこが前提かを分かるようにした。
- **feedback 簿 + 進捗ログ** で複数セッションにわたる流れを維持した; 本報告の数値は `AI-report-evidence/` 内のファイルまで追跡できる。
- **AI の稼働約 15.8 時間（41.1 エージェント時間）に対し、人の時間は約 3 時間** — 読み込み・採点の大部分は有識者と顧客の役割が担い、人はゲートでの判断に集中した（§3.4）。

### 4.2 うまくいかなかった点、実務では改善が必要な点

- **共通の規約が遅れた。** API の規約と共通の CSS は、作業を分けた *後* に用意したため、統合で一往復が余分にかかり、見落としを生んだ（誤り 5、6、9）。実務では: 分散させる前に、規約・枠組み・自動検査を書く。
- **レイアウトの出典が二つ並存** （WF MD 内の ASCII ブロックと HTML）が、15件中14件のワイヤーフレームに残っている; 「ずれたら HTML + SPEC に従う」と規則を記録し、ASCII は凍結したが、整理はしていない（有識者 W-m07、LAB-5 に残す）。実務では: 画像の出典は一つだけ残す（Figma または HTML）。
- **並行の流れで書かれた部分は、主に PL が grep / スクリプトで確認しただけ**（エラーコード、JSON のキー、バッジ、リンク）。構文の正しさと相互の一貫性は検査できたが、業務として正しいかは有識者がサンプルを読むことでしか確認できなかった。12画面の Spec は長く、有識者も全行は読めなかった。
- **顧客はAIが演じている。** 回答は妥当だが、実在の 経理部 / 経営陣 の代わりにはならない; いくつかの質問（後入力の取引への 請求 の記録方法、代行の人員、E-14）はまだ未決のまま。設計が正しいのは、前提が正しい範囲まで。
- **自動のスキル・パイプラインは実行しなかった**ため、既存の検査ゲートを失った; 有識者のゲートで補ったが、ゲートは手作業でトークンもかかる。
- **時間 / トークンの制約**: Screen Specification があるのは 12 / 70 画面のみ; ワイヤーフレームはあるが spec がない画面が3つ; DEP-01..17 の依存関係はまだ一覧のレベル。日本語版 `ja/` は AI が翻訳（並列10本）し、スクリプトで後処理（行数、`|` の数、コードブロック、ラベル、数値、リンク）— 日本語話者による業務内容のレビューはまだ。
- **未コミットのファイルにスクリプトで一括操作をしたため、一つのファイルを失った**（誤り 14）。セッションの履歴から再構築できたが、それは幸運だった。実務では: 小さく、こまめにコミットし、修正スクリプトは必ず読み込んでから書き込む。
