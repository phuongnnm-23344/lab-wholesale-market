# ログの規約

> **ISO 様式 BM-2-901-53 v01 の sheet `Logs` の内容をそのまま維持。** ログの規約はプロジェクト **全体** に適用されるため、一つの function に属さないよう独立したファイルに分けた — そのため、ひな形 [BM-2-901-53](../../../specs/_templates/BM-2-901-53-technical-design-template.md) には `Log` の項目がなくなった。
>
> **まだ標準として使えない。** 本ファイルは専門家による確認待ち — [3節](#3-専門家への確認事項) を参照。元の様式には、検証済みの内容の誤りが少なくとも一つある（2節）。

---

## 1. 形式

| Date time | Log type | Category Name | Message |
|---|---|---|---|
| `[yyyy-mm-ddTHH:MM:SS.000]` | `[INFO]` | `[default]` | ***REMOVED*** |

- 各フィールドは角括弧 `[...]` で囲む。ただし `Message` は除く。
- 元の様式は、フィールド間の区切り文字、タイムゾーン、`Category Name` の値の出所（例では `default` を使用）を **規定していない**。

---

## 2. Log type

元の様式の原文。確認時に照合できるよう、**誤りの箇所もそのまま残す**:

| Log type | 説明（様式の原文） | 備考 |
|---|---|---|
| TRACE | ***REMOVED*** | **誤り** — log4j における `INFO` の説明である; `TRACE` は *"***REMOVED***"* でなければならない |
| DEBUG | ***REMOVED*** | 正しい |
| INFO | ***REMOVED*** | **誤り** — `ERROR` の原文と同一 |
| WARN | ***REMOVED*** | 正しい |
| ERROR | ***REMOVED*** | 正しい |
| FATAL | ***REMOVED*** | 正しい |

使い方の提案（log4j に基づく、**未決裁**）:

| Log type | 使用する場面 |
|---|---|
| `TRACE` | DEBUG より詳細なイベント — 深い追跡のときだけ有効にする |
| `DEBUG` | デバッグに役立つ詳細なイベント |
| `INFO` | アプリの大まかな進行の節目（処理の開始 / 終了） |
| `WARN` | リスクのある状況、まだエラーではない |
| `ERROR` | エラーが発生したが、アプリはまだ動き続けられる |
| `FATAL` | 非常に重いエラー、アプリを停止させる必要がある |

## 3. 専門家への確認事項

| # | 質問 | 質問の理由 | 回答 |
|---|---|---|---|
| 1 | ISO 原様式の `TRACE` と `INFO` の説明は誤っている — 様式を修正するか、プロジェクトが独自に上書きするか？ | ISO の押印付きの様式の修正は文書管理部門を経る必要がある; そのままにすると、プロジェクトごとに解釈が分かれる | |
| 2 | フィールド間の区切り文字、タイムゾーンは何を使うか（UTC か現地時刻か）？ | 統一しないと、サービス間のログを時刻順に統合・比較できない | |
| 3 | `Category Name` はどこから取るか — モジュール名、クラス名、それとも固定のカテゴリ一覧か？ | 様式の例は `default` のみで、規則を導けない | |
| 4 | ログに書くことが **禁止** されるもの（パスワード、トークン / JWT の原文、カード番号、個人情報）は何か？ | 様式には書かれていない; データ漏えいのリスクであり、明確な禁止の一文が必要 | |
| 5 | ログの保存先、保存期間、誰が閲覧するか？ | ないと、運用時に検証できない | |
| 6 | ログの規約は **spec 一式** に属するか、それともプロジェクトの **コーディング規約** に属するか？ | 本ファイルを `03-specs/_common/` に残すか、技術文書へ移すかを決める — `ISS-35` を参照 | |

## 4. Product A（LAB-4）への適用

> `sun-asterisk-internal/spec-standards` の `main` ブランチ（コミット `72c1dda`、2026-11-05）からのコピー。1〜3節は標準の文書をそのまま維持し、本節にプロジェクトでの適用方法を記載する。

| # | 3節の質問 | プロジェクトでの扱い | 確定箇所 |
|---|---|---|---|
| 1 | `TRACE` / `INFO` の説明が誤り | プロジェクトは2節の「使い方の提案」の表を使い、様式の原文は使わない | システム観測に関する ADR（P2-A） |
| 2 | 区切り文字、タイムゾーン | 未確定。PLの前提: UTC で保存、JST で表示; 1行の JSON 形式 | ADR (P2-A) |
| 3 | `Category Name` | 未確定。PLの前提: 業務モジュールの名前（例 `trade`、`lot`、`settlement`） | ADR (P2-A) |
| 4 | 禁止する記録内容 | パスワード、PIN、トークン、入金CSVの内容、参加者の個人データを書かない（APPI、09-06） | ADR (P2-A) |
| 5 | 保存先、保存期間 | アプリのログは **監査ログ**（FR-AUDIT-01、7年保存、追記のみ）とは別にする; アプリのログの保存期間は未確定 | ADR (P2-A) |
| 6 | spec に属するか、コーディング規約か | LAB-4では `specs/_common/` に置く | — |
