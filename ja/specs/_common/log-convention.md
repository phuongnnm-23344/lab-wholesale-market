# ログの規約

> ログの規約はプロジェクト全体に適用するため、各 Technical Design ではなく `_common/` に置く。項目の枠は社内標準 spec-standards（非公開）に準拠し、内容は Product A が実際に使う部分だけをプロジェクト自身の言葉でまとめた要約である。
>
> 未確定の点がある — [3節](#3-未確定の点) を参照。プロジェクトでの暫定の扱いは4節に記載する。

---

## 1. 形式

| 項目 | プロジェクトでの扱い |
|---|---|
| 日時 | ISO 8601、UTC で保存、JST で表示 |
| ログレベル | 2節の6レベルのいずれか |
| カテゴリ | 業務モジュールの名前（例 `trade`、`lot`、`settlement`） |
| 内容 | 短い文 + リクエストの `traceId` |

- 1件を1行の JSON とし、サービスをまたいで集約・絞り込みできるようにする。

---

## 2. ログレベル

| レベル | 使う場面 |
|---|---|
| `TRACE` | ごく詳細な追跡。深い調査のときだけ有効にする |
| `DEBUG` | 開発時のデバッグに役立つ情報 |
| `INFO` | 処理の主な節目（開始、終了、結果） |
| `WARN` | 異常の兆候はあるが、処理は正しく続いている |
| `ERROR` | 処理が失敗したが、システムは動き続ける（例 `traceId` 付きで `E-CMN-004` を返す） |
| `FATAL` | プロセスを停止せざるを得ないエラー |

---

## 3. 未確定の点

| # | 論点 | 確定が必要な理由 | 回答 |
|---|---|---|---|
| 1 | 標準様式のログレベル説明に誤りがある — プロジェクトが2節の表を使ってよいか | プロジェクトごとに直すと、ログレベルの解釈がそろわない | |
| 2 | 1行の形式とタイムゾーン | 複数サービスのログを時刻で集約・比較できる必要がある | |
| 3 | カテゴリの取り方 | 規則がないと業務ごとにログを絞り込めない | |
| 4 | ログに書いてはいけないデータ | 秘密情報・個人データの漏えいを防ぐ | |
| 5 | 保存先、保存期間、閲覧者 | 運用と検証に必要 | |
| 6 | ログの規約は spec 一式か、コーディング規約か | 本ファイルの置き場所が決まる | |

---

## 4. Product A（LAB-4）への適用

> 1〜3節はプロジェクトが自ら書いた要約（0.3.0 以降）。本節に未確定の各点のプロジェクトでの扱いを記載する。

| # | 3節の質問 | プロジェクトでの扱い | 確定箇所 |
|---|---|---|---|
| 1 | `TRACE` / `INFO` の説明が誤り | プロジェクトは2節のログレベル表を使い、様式の説明は使わない | システム観測に関する ADR（P2-A） |
| 2 | 区切り文字、タイムゾーン | 未確定。PLの前提: UTC で保存、JST で表示; 1行の JSON 形式 | ADR (P2-A) |
| 3 | `Category Name` | 未確定。PLの前提: 業務モジュールの名前（例 `trade`、`lot`、`settlement`） | ADR (P2-A) |
| 4 | 禁止する記録内容 | パスワード、PIN、トークン、入金CSVの内容、参加者の個人データを書かない（APPI、09-06） | ADR (P2-A) |
| 5 | 保存先、保存期間 | アプリのログは **監査ログ**（FR-AUDIT-01、7年保存、追記のみ）とは別にする; アプリのログの保存期間は未確定 | ADR (P2-A) |
| 6 | spec に属するか、コーディング規約か | LAB-4では `specs/_common/` に置く | — |
