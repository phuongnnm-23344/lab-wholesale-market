## 2. AI の使い方

### 2.1 役割を3つに分け、一人が調整する

| 役割 | 担当 | 禁止事項 |
|---|---|---|
| **Project Leader (PL)** | すべての成果物の作成、フィードバックに基づく修正、フィードバック簿 / 決定 / 顧客への質問の記録 | 自分の成果物の採点、顧客の代わりに回答すること |
| **有識者（Expert）** | 受講者が各ゲートで指示した基準で採点し、結論を出す: RELEASE / 条件付き RELEASE / RELEASE 不可 | PL の成果物を修正すること |
| **顧客（模擬）** | 桜水産市場とエンドユーザーを演じる: 質問への回答、前提とワイヤーフレームへの意見 | RFP 外の回答に `[Giả lập]`（日本語版では【模擬】）のラベルを付けないこと |

3つとも AI エージェントである。メインのチャットは役割間の受け渡しと受講者への報告だけを行う。分けた理由: AI が自分の成果物を採点すると、すでに信じていることを確認するだけになりやすい。Gate 1 では、PL が自己確認で見落とした Critical 2件を有識者が見つけた。

### 2.2 作業の指示方法

- 毎回、何をするか、どのファイルを修正してよいか、どのファイルは読むだけか、完了の条件、最後の報告の固定様式を明示した。
- 3本の AI を並行で動かすとき（P3 の spec、ワイヤーフレーム HTML）は共通ブリーフを用意した: 文書の標準、必須の内容、どの流れがどのファイルを修正するか。共通ファイルは PL だけが統合する。
- 共通の決定は、複数箇所を直す前に一つの文書にまとめた。例: Gate 1 の後、決定 D1–D13 を、同時に直す5つの文書の唯一の出典にした。
- 顧客が未回答の点は AI に推測させず、質問 + 暫定前提 + 前提が誤っていた場合の影響として記録した。
- 各セッションで、PL は作業前に課題のルール、作業メモ、フィードバック簿を読み直した。

### 2.3 ツール

Skill は主に枠組みとチェックリストとして使った。成果物を会社の文書ひな形に合わせる必要があるため。最も役立ったのはパリティ確認: AI が文書を読まずにプロトタイプのコードを記述し直し、それを文書と比べる。ほかに小さなスクリプトが4つ: ワイヤーフレームと図の画像出力、API Design の検査、リンクの検査。

### 3.2 受講者が決めたこと

私はすべての行を読むことはせず、範囲・構成・方向を変える点だけを決めた; それ以外は PL が決めて記録し、有識者が確認した。誰がどの点を決めたかは PREMISE §5 と [決定ログ](../../AI-report-evidence/logs/decision-lab4-excerpt.md) にある。

- **LAB-4 の開始時:** 原本はベトナム語; spec を完全に作る画面は10（課題は「中核となる画面」のみを要求）; 文書の標準は一つ; 有識者の採点基準。
- **前提:** to-be のアーキテクチャは AWS Tokyo、プロトタイプは試作にすぎない; 画面 SC-01-02 は 許可（仲卸の許可）と 承認（売買参加者の資格）の二つのブロックに分ける。
- **Gate 1 の後:** Database Design を9ファイル + 総括ファイル1つに分割; 社内の決裁に 承認 の文字を使わない; 顧客の意見に従いワイヤーフレームを1つ追加; 質問 E-14 はワークショップまで未決とし、設計は両方の分岐を描く。
- **Gate 2 の後:** Screen Specification を70画面まで広げない; 残りは LAB-5 へ。
- **Gate 3 の後:** 3つのゲートを通った ADR は Accepted に。ただし ADR-006 は E-14 待ち。
- **ワイヤーフレーム:** スタイルの見本を渡し、試作画面を決裁してから残り14画面を作らせた。
- **リポジトリと翻訳:** ローカルコミットは可、push とマージは個別に確認; 日本語版は `ja/` に完全版を置く。

PL は範囲を変えない点を自分で決めた。例: 争いのある引渡しの2画面を spec に追加（12画面）。課題のルール上、最終決定を人が行う点だから; 追加作業（約 0.5 MM）は 15% のバッファ内なので価格は維持; 3本の流れを統合するときに API の共通規約を確定。

顧客（模擬）は3回回答した（前提 22点、ワイヤーフレームへの意見 32件 + 回答 5件、spec の質問 31件）; 回答はラベル付きの前提としてのみ使った。

## 4. 自己評価

### 4.1 うまくいった点

- **書く人と採点する人を分けたので、誤りが早く表に出た。** Gate 1 は23件、Gate 2 は13件、Gate 2 完了時は Minor 8件; Gate 3 では Critical はなく、Major 3件はいずれも提出用の付属文書とリポジトリのセキュリティにあり、設計の内容にはなかった。
- **共通ブリーフとファイルごとの修正権限**: 並行する流れが互いに上書きしなかった。
- **一つの出典から一つのコマンドで複数の出力**（ワイヤーフレーム HTML → PDF、PNG、spec の画像）: 画像の番号は常に spec の表と一致する。
- **未確定の点は影響を記した質問にした**; 模擬の回答には出典ラベルを付けた。
- **AI の稼働約 15.8 時間（41.1 エージェント時間）に対し、人の時間は約 3 時間**: 読み込みと採点は有識者と顧客の役割が担い、人はゲートでの判断に集中した。

### 4.2 不十分だった点と、実務での改善

- **共通規約が遅れた**ため、統合に1回分の手間がかかり、漏れが出た（誤り 5）。実務では: 作業を分ける前に規約、枠組み、検査を用意する。
- **機械の検査は構文の正しさしか捕まえられず、意味の正しさは捕まえられない**（誤り 7）。業務上の正しさは有識者の抜き取り読みだけ; 12画面の spec は長く、有識者もすべては読んでいない。日本語版は、日本語話者による業務内容のレビューをまだ受けていない。
- **顧客は AI の役割演技**: もっともらしいが、実際の経理部・経営陣の代わりにはならない; いくつかの質問は未決のまま。設計の正しさは前提の正しさに依存する。
- **ワイヤーフレームの画像の出典が2つ残っている**（ASCII ブロックと HTML）。「ずれたら HTML に従う」という規則はあるが、整理はまだ。実務では: 出典は一つだけにする。
- **範囲に穴がある**: spec があるのは 12 / 70 画面; 未仕様化の依存はまだ一覧のレベル。
- **コミット前のファイルをスクリプトで一括修正**して、ファイルを1つ失ったことがある。セッションの履歴から復元できた。実務では: 小さく頻繁にコミットし、スクリプトは読んでから書く。
